# Boardmark 제품 아이덴티티: 프로젝트 기반 화이트보드 작업 공간

작성일: 2026-09-18

상태: **보드 중심 IDE 앱이라는 제품 아이덴티티, 자유로운 보드 파일 위치, 첫 버전의 JSON 저장 형식 확정. 세부 저장·실행 계약과 전환 계획은 후속 설계.**

## 1. 제품 정의

> Boardmark는 프로젝트에 필요한 문서, 코드, 도구, 실행 결과와 외부 서비스를 하나의 무한한 화이트보드에 구성하고 연결하는 IDE 앱이다.

프로젝트는 폴더 단위로 만들거나 연다. 파일 디렉터리로 실제 자료를 탐색하며, 사용자의 작업 단위는 화이트보드다. 하나의 프로젝트 안에서 목적에 따라 여러 보드를 구성하고, 각 보드에 필요한 콘텐츠와 도구를 원하는 위치와 크기로 배치한다.

화이트보드 자체도 일반 파일로 관리한다. 보드 파일은 배치와 참조, 보드가 소유한 콘텐츠를 기록하는 프로젝트 구성 요소다. 신규 보드를 만들면 사용자가 선택한 위치에 파일로 저장한다. 프로젝트 루트나 하위 폴더 등 어디에 두든 보드의 기능과 의미가 달라지지 않으며, 전용 보드 폴더나 별도 목록 등록을 요구하지 않는다. 사용자는 앱에서 프로젝트를 열고 보드 파일을 만들거나 열어 작업한다.

Markdown을 보드에 붙이고 편집하는 경험은 계속 제공한다. 다만 Markdown은 이제 제품이 제공하는 콘텐츠 기능 중 하나다. 파일 형식이나 특정 도메인이 제품 전체의 범위와 정체성을 결정하지 않는다.

프로젝트·파일·편집·실행을 다루는 IDE 앱을 만들며, 작업에 필요한 화면을 펼치는 중심 공간은 화이트보드다. VS Code 같은 IDE의 프로젝트·파일 탐색 경험을 참고하고, 기능은 이 작업 방식에 맞춰 단계적으로 구현한다.

## 2. 이 문서의 우선순위와 현재 구현

이 문서는 [2026-09-09 제품 방향](README.md)의 제품 정의와 장기 방향을 대체한다. 이후 제품 기획에서 다음 설명이 충돌하면 이 문서를 우선한다.

- Boardmark 전체를 Markdown 캔버스 에디터로 한정하는 설명.
- 모든 콘텐츠와 작업을 하나의 Markdown 원문으로 표현해야 한다는 제품 차원의 전제.
- DDD, 설계 문서 또는 특정 업무를 제품 전체의 범위로 삼는 설명.

현재 구현의 [DB Markdown 저장·편집 계약](../architecture/db-markdown-api.md)은 전환 구현 전까지 해당 모드에 적용된다. 이 문서 추가만으로 파일 저장, DB 마이그레이션, 외부 서비스 연결, 명령 실행 기능이 구현되거나 기존 저장 동작이 바뀌지는 않는다.

IDE 앱이라는 제품 아이덴티티, 보드 자체의 파일 관리, 고정 폴더 없이 사용자가 저장 위치를 선택하는 방향은 확정되었다. SQLite와 JSON을 비교한 뒤 사용자는 첫 버전의 JSON 저장을 선택했다. 보드 파일은 `.boardmark` 확장자와 UTF-8 JSON을 사용한다. 선택 이유와 검토한 대안은 5.2절에 기록한다. 세부 스키마, DB의 보조 역할, 기존 문서 이전 방식, 기본 실행 호스트는 아직 결정하지 않았다. 기존 구현의 제약을 새 제품의 영구적인 정의로 사용하지 않는다.

## 3. 사용자의 작업 경험

사용자는 프로젝트 폴더를 열고 파일 트리를 탐색한다. 작업할 보드를 만들거나 열고, 필요한 파일·자료·도구를 배치한다. 같은 프로젝트의 자료를 서로 다른 작업 보드에서 활용할 수 있다.

보드에 배치할 수 있는 대상의 방향은 다음과 같다. 아래 목록은 확장 방향이며 구현 완료 목록이 아니다.

| 대상 | 보드에서 하는 일 |
|---|---|
| Markdown, 포스트잇, 설명 문서 | 내용을 작성하고 읽는다. |
| 이미지 | UI 시안이나 참고 자료를 배치하고 비교한다. UI 시안의 첫 범위는 이미지다. |
| 코드 에디터 | 프로젝트 파일을 열고 편집한다. |
| 코드 기반 다이어그램 | Mermaid처럼 소스를 작성하고 시각화한다. |
| OpenAPI·Swagger | 명세를 문서 형태로 읽거나 특정 API 문서 페이지를 작업 옆에 둔다. |
| 터미널 | 작업에 필요한 명령을 실행하고 출력을 확인한다. |
| 실행 버튼 | 특정 Makefile target 등 정의된 CLI 작업을 실행하고 결과를 확인한다. |
| HTML·실행 미리보기 | 화면이나 실행 결과를 작업 맥락 안에서 확인한다. |
| 외부 서비스 패널 | Grafana 패널 같은 외부 화면과 데이터를 작업 옆에 배치한다. |

예를 들어 개발 보드에는 UI 이미지·소스 코드·API 문서·테스트 실행 버튼을, 운영 보드에는 Grafana 패널·로그·운영 문서·진단 명령을 모을 수 있다. 같은 공간 구성 원칙을 다른 업무에도 적용할 수 있어야 한다.

보드 다시 열기는 배치와 작업 대상을 복원하는 경험을 지향한다. 실행 프로세스나 외부 서비스의 과거 상태까지 그대로 복원된다고 간주하지 않는다. 구체적인 복원 범위는 도구별 생명주기 설계에서 정한다.

## 4. 제품을 설명하는 공통 개념

아래는 제품 개념의 구분이며 확정된 패키지 구조나 API 스키마가 아니다.

| 개념 | 책임 |
|---|---|
| 프로젝트 | 기준 폴더, 파일 탐색, 여러 보드와 프로젝트 작업의 맥락. |
| 리소스 | 파일, 이미지, URL, 명세 등 실제 작업 대상. |
| 보드 | 작업에 필요한 대상을 어떤 위치·크기·보기 방식으로 구성하고 연결할지. |
| 도구·표현 | 같은 대상을 읽고 편집하거나 실행하는 방식. |
| 실행·연결 상태 | 프로세스, 터미널 세션, 외부 서비스 연결과 현재 상태. |

같은 `openapi.yaml`을 코드 에디터와 API 문서 화면으로 각각 볼 수 있다. 같은 소스 파일을 서로 다른 보드에 배치해도 동일한 파일을 참조하는 경험을 지향한다. 같은 리소스를 참조하는 배치와 독립 사본을 만드는 동작은 구분해야 한다.

보드에서 참조 화면을 제거하는 일과 실제 파일을 삭제하는 일도 구분한다. 보드 자체가 소유하는 메모의 삭제와 참조된 프로젝트 파일의 삭제는 같은 동작이 아니다.

## 5. 저장 정책의 전환 방향

보드 자체의 영속 원본은 사용자가 저장한 보드 파일로 관리한다. 저장 정책은 각 대상의 소유권과 사용 경험을 따라 설계한다. 모든 대상의 내용을 보드에 복제하거나 Markdown에 넣어야 한다는 전제를 두지 않는다.

| 대상 | 원본과 보드 저장의 역할에 관한 방향 |
|---|---|
| 화이트보드 자체 | 보드 파일에 배치·참조·보기 설정과 보드가 소유한 콘텐츠를 저장한다. |
| 보드 안에서 직접 작성한 메모 | 보드가 내용을 소유할 수 있다. |
| 프로젝트 파일 | 실제 파일을 작업 대상으로 삼고, 보드는 참조와 보기 설정·배치를 보관한다. |
| 외부 서비스 | 외부 서비스가 제공하는 자료와 보드의 연결 대상·표시 설정을 구분한다. |
| 명령과 터미널 | 작업 정의·배치와 실행 중인 프로세스·세션을 구분한다. |
| 검색·미리보기 캐시 | 원본과 재생성 가능한 파생 데이터를 구분한다. |

저장해야 할 작업 맥락과 일시적인 상태를 구별하고, 같은 리소스에 대한 여러 화면이 서로 다른 원본을 만드는 구조를 피한다. 외부 파일 변경, 이름 변경, 이동, 참조 해제, 편집 충돌과 복구는 후속 저장 설계에서 명시한다.

DB는 검색·캐시·복구 이력 등 보조 역할이 필요할 때 검토하고, 보드 파일과 별개의 편집 원본으로 중복 소유하지 않는다. 기존 문서를 변환하거나 정리하는 작업에는 별도의 이전·복구 계획이 필요하다.

### 5.1 저장 위치 — 확정

보드는 다른 파일처럼 사용자가 원하는 위치에 생성·저장한다. `.boardmark/boards/` 같은 전용 폴더 배치는 요구사항이 아니다. 파일의 위치나 특정 설정 파일에 등록되었는지가 보드 여부를 결정하지 않는다. 이동·이름 변경 시 참조를 어떻게 유지할지는 별도 설계하되, 참조 관리의 편의를 위해 보드 위치를 제한하지 않는다.

### 5.2 확장자와 저장 형식 — 첫 버전 JSON 확정

사용자가 첫 버전은 JSON으로 진행하기로 확정했다. 보드 파일의 내용이 주로 배치·참조·설정·짧은 메모라는 현재 범위에 맞춘 선택이다. 저장 형식의 확정이 구현 완료나 세부 스키마 확정을 뜻하지 않는다.

- **확장자:** `.boardmark`. 예: `overview.boardmark`, `design/payment.boardmark`.
- **내용:** UTF-8 JSON. 앱에서 작성·저장하고, 사람과 AI도 일반 텍스트로 읽고 수정할 수 있게 한다.
- **식별과 버전:** 파일 안에 `format: "boardmark"`와 정수 `version`을 명시하는 방식을 제안한다. 확장자만 믿지 않고 내용을 검증하며, 향후 버전 전환의 기준으로 사용한다.
- **직렬화:** 들여쓰기와 필드 순서를 일관되게 유지하고, 의미 없는 배열 재정렬을 피해서 변경 내용을 확인하기 쉽게 한다.
- **역할:** 보드가 소유한 데이터와 다른 리소스의 참조·배치를 저장한다. 프로젝트 파일이나 외부 서비스 데이터를 기본적으로 파일 안에 복제하지 않는다.

JSON은 배치·도구별 설정·참조 같은 구조화된 데이터를 표현하고 검증하기에 적합하다. 긴 Markdown이나 코드의 직접 작성에는 별도 원본 파일을 참조하는 흐름을 활용할 수 있다. 댓글 문법이 없는 점과 여러 줄 문자열의 이스케이프는 일반 JSON의 작성상 제약으로 고려한다.

SQLite도 보드 하나의 파일 형식으로 사용할 수 있다. `.boardmark` 확장자를 가진 SQLite 파일을 원하는 위치에 두는 방식은 중앙 DB에 모든 보드를 보관하는 기존 모델과 다르다. SQLite는 트랜잭션과 부분 갱신, 관계 조회를 제공하므로 큰 보드의 빈번한 부분 저장이나 보드 내부에 많은 데이터를 보관해야 하는 경우에 검토 가치가 있다. 근거: [SQLite의 애플리케이션 파일 형식 안내](https://www.sqlite.org/appfileformat.html).

첫 버전은 원본 코드·명세·이미지를 외부 파일로 참조하고, 보드 구조를 일반 텍스트로 확인·편집하며 Git에서 변경을 비교하는 편의를 우선해 JSON을 사용한다. JSON 저장의 중단·충돌 대응은 별도 구현이 필요하며, 텍스트 형식 자체가 안전한 저장이나 의미상 올바른 병합을 보장하지 않는다. SQLite는 검토한 대안으로 남기며, 향후 재검토가 필요하면 실제 크기·저장 비용·조회 요구를 근거로 별도 결정한다. 지금 두 저장 백엔드를 동시에 구현하지 않는다.

기존 `.boardmark.json`은 현재 DB 문서의 이동용 묶음(`boardmark-bundle-v1`)에 사용한다. 새 `.boardmark` 보드와 기존 묶음은 목적과 포맷을 구분한다. 이 결정만으로 기존 내보내기·가져오기 동작을 바꾸지 않는다.

로컬 파일 참조는 **보드 파일이 있는 폴더를 기준으로 한 상대 경로**를 우선 검토한다. 이것도 아직 제안이다. 보드만 이동할 때의 경로 갱신과 앱 밖에서 이동되어 참조가 끊긴 경우의 복구를 함께 설계해야 한다.

## 6. 연결된 설계는 첫 활용 사례

사이트맵, UI 시안, 유스케이스, API 스펙, 시퀀스 다이어그램, 바운디드 컨텍스트, Aggregate·Entity·Policy·Event, ERD와 데이터베이스 스키마를 하나의 보드에서 유기적으로 연결하는 것이 첫 활용 사례다.

설계는 Mermaid처럼 코드를 작성하고 변환하는 경험을 우선한다. DDD 요소마다 수동으로 카드를 생성하는 방식으로 작성 경험을 고정하지 않는다. 전용 DDD 문법을 만들지, 기존 표기법을 조합할지는 별도 검토 대상이다.

장기적으로는 자료 전체뿐 아니라 다이어그램 내부 요소, API 엔드포인트 같은 세부 대상도 식별하고 연결할 수 있어야 한다. 동일한 개념을 여러 곳에서 참조하는 것과 서로 다른 대상 사이의 관계를 구분한다. 예를 들어 Aggregate와 데이터베이스 테이블은 같은 이름이라는 이유만으로 같은 식별자를 갖지 않는다.

공통 기반은 배치·참조·연결·탐색을 지원하고, DDD 용어나 API 스키마의 구체적인 의미는 해당 기능에서 다룬다. OpenAPI 통합은 이 방향의 첫 구현 대상으로 논의되었으며, 제품 전체를 API 설계 도구로 제한하지 않는다.

## 7. 이후 설계에서 결정할 사항

1. **프로젝트와 보드 저장:** JSON 보드의 세부 스키마·버전 전환·저장 중단 대응, 리소스 식별, 상대 경로, 이름 변경·이동, 보드 복제·공유·내보내기. 저장 위치는 자유이며 고정 폴더 규칙을 도입하지 않는다.
2. **기존 문서의 전환:** DB 문서와 기존 파일 모드의 보존, 가져오기, 이전·복구와 공존 범위.
3. **호스트 역할:** desktop·web·VS Code에서 파일 접근과 실행을 맡는 주체 및 기능 차이.
4. **도구 계약:** 파일 기반 도구, 보드 내 콘텐츠, 외부 패널, 실행 도구의 생성·저장·연결 해제·복원.
5. **편집과 입력:** 보드 이동·선택과 도구 내부의 텍스트 선택·단축키·스크롤, 저장·Undo·충돌 처리의 소유권.
6. **명령 실행:** 작업 정의, 작업 디렉터리, 실행·중지·중복 실행, 출력과 종료 상태, 보드 재개방 시 처리.
7. **외부 서비스 연결:** 서비스별 표시 방식, 인증과 권한, 갱신·실패 상태. 모든 페이지를 동일한 방식으로 임베드할 수 있다고 가정하지 않는다.
8. **큰 보드의 사용성:** 프로젝트 탐색과 보드 탐색, 저장된 뷰, 여러 도구가 동시에 열릴 때의 렌더링·실행 비용.

이번 문서 작업은 위 계약이나 구현 순서를 확정하지 않는다. 다음 기능에 필요한 범위부터 검증하며, 미래 확장만을 위한 범용 프레임워크를 먼저 만들지 않는다.
