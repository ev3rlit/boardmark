# DB 작업 공간 구현·검증 기록

검증일: 2026-09-09. 범위는 로컬 단일 서버의 DB Markdown 원본, 웹 GUI와 별도 AI CLI, 자동 객체 편집권이다. 공개 배포·commit·push는 하지 않았다.

## 시작 상태와 구현 단계

시작 시 `main...origin/main`, HEAD `018cfcf`, 사용자 변경 없는 상태를 확인했다. AGENTS.md, RULE.md, DESIGN.md와 저장·편집·셸·관련 기획을 읽었다. 기존 편집 compiler/resolver, 로컬 드래그·리사이즈 미리보기, Undo, 이미지 bridge를 재사용했다. 파일 저장을 서버 저장으로 가장하는 어댑터는 만들지 않았다.

Node 24.19.0과 Corepack pnpm 10.6.2로 잠금 파일 기준 설치를 완료했다. 전역 pnpm 11의 다른 설치 정책과 구분해 프로젝트 지정 버전을 사용했다. 변경 전 HEAD를 별도 worktree에서 같은 의존성으로 검사했을 때 361개 중 35개 테스트가 실패했고 VS Code에 기존 타입 오류 7개가 있었다. 과거 코드 조사만으로 화면·성능이 검증되었다고 취급하지 않았다.

1. **원본과 계약:** SQLite에 원문·문서 버전·편집권 발급 정보·요청 결과·이력·첨부를 보관한다. 공유 편집 처리를 `canvas-edit`로 옮기고 `canvas-api`에 명령·오류·HTTP 계약을 둔다. 웹과 CLI는 같은 서버를 호출한다.
2. **동시성과 복구:** 서버가 최신 원문으로 영향 범위와 관계를 계산하고 짧은 트랜잭션 안에서 검증·저장한다. 객체별 자동 편집권, 이전 변경 기준 검사, 요청 중복 방지, 재시작 무효화, 역변경 Undo를 구현했다. 연결이 끊긴 초안과 응답이 유실된 요청은 별도로 보존한다.
3. **제품 화면:** 서버 문서 목록·생성·열기·이름 변경·가져오기·내보내기, 저장/연결 상태, 복구 행동을 추가했다. 이미지 prompt를 미리보기 폼으로 교체했다. 선택 도구·숫자 위치/크기 입력·좁은 화면 배치·짧은 전환·reduced-motion을 실제 화면에서 확인했다.
4. **검증 중 수정:** 구형 YAML 직렬화 기대값, Mermaid mock, Sandpack snapshot/이미지 디코딩 mock, Windows 경로 기대값, jsdom 선택 영역 측정을 현재 계약에 맞췄다. 기대값 변경 중 드러난 그룹 복제의 원래 노트 참조 결함은 공통 파서로 고쳤다. 붙여넣기의 기존 노트 관계도 서버가 편집권 대상으로 계산하도록 보강했다.

## 자동 검증

| 검사 | 결과 |
|---|---|
| `corepack pnpm test` | 51개 파일, 386개 테스트 통과; 처리되지 않은 테스트 오류 없음 |
| `corepack pnpm typecheck` | 통과 |
| `corepack pnpm build:web` | 통과 |
| `corepack pnpm build` | API·CLI·desktop·web 빌드 통과 |
| `corepack pnpm --filter @boardmark/vscode build:webview` | 통과 |
| `corepack pnpm --filter @boardmark/vscode build:extension` | 통과 |
| 서버/CLI 패키지 | 실제 SQLite/HTTP/별도 자식 프로세스 테스트, esbuild 빌드 통과 |

Vite의 큰 청크 경고는 남아 있다. 테스트를 건너뛰거나 시간 제한만 늘려 기존 실패를 숨기지 않았다. Sandpack 테스트는 iframe snapshot 메시지와 shell 합성 계약을 검사하지만 실제 외부 Sandpack 서비스의 모든 네트워크·스크린샷 동작을 보장하는 검사는 아니다.

자동 검사의 주요 경계:

- BOM·CRLF·주석·frontmatter·무관한 본문 보존, 원문 그대로 내보내기, DB 재접속, 첨부 묶음의 다른 DB 복원.
- 동일 객체 독점, 독립 객체의 옛 문서 버전 변경 허용, 다중 확보 실패 시 권한 누수 없음, 일부 권한만 가진 다중 변경 거절.
- 연결선 생성/노트 삭제, 그룹·붙여넣기의 관계 범위, 객체가 바뀌었다가 원래 텍스트로 돌아온 경우에도 옛 기준 거절.
- 편집권 만료·이전 소유자 반납·재시작 세대, 같은 DB의 두 서버 실행 거절.
- 동일 요청의 결과 재생·다른 내용의 ID 재사용 거절, CLI 새 프로세스의 원래 요청 복구.
- CLI 대기 시간 제한·취소, 대기 중 대상 변경 후 옛 제안 거절.
- 웹 승인 전 편집 차단, 승인 대기 입력 보존, Escape 이후 늦은 편집기 열림 방지.
- 웹 저장/Undo 응답 유실 후 중복 없는 복구, 재동기화 시 활성 초안·선택·카메라 유지, 복구 초안 덮어쓰기 방지와 별도 보관.
- 자신의 변경만 Undo/Redo하고 다른 노트의 AI 변경 보존.

강제 종료 검사는 실제 API 자식 프로세스에 큰 저장 요청을 보내고 종료한 뒤 재시작한다. 원문·이력·중복 요청 기록이 함께 미확정 또는 함께 확정인지, SQLite `integrity_check`가 정상인지 확인한다. 정확한 디스크 쓰기 명령 사이에 전원을 끊는 시험은 아니며 모든 하드웨어 고장 상황의 보장을 뜻하지 않는다.

## 실제 웹·CLI·DB 프로세스

개발 웹 `127.0.0.1:5173`, API `127.0.0.1:4317`, 실제 `.boardmark/boardmark.sqlite`, 별도 CLI 프로세스를 사용했다. 브라우저는 agent-browser의 독립 `boardmark-web` / `boardmark-peer` 세션이다. 마지막에는 빌드 API `node apps/server/dist/main.mjs`로 재시작했다.

| 사용자 흐름 | 확인 결과 |
|---|---|
| 웹 문서 생성 → 새로고침 → CLI 조회 | 같은 문서 ID·저장 본문 복원 |
| 웹에서 A 편집 중 다른 웹에서 A 편집 | 두 번째 편집기 진입 차단; 읽기 가능 |
| 웹에서 A 편집 중 별도 CLI로 A 수정 | `locked` 오류, A 덮어쓰기 없음 |
| 웹 A 초안 중 CLI가 B 수정 | 웹에 B 변경 반영, A 편집기와 초안 유지; A 완료 후 둘 다 DB 보존 |
| 실제 포인터 이동·리사이즈 | CLI 조회에서 위치/크기 저장 확인; 포인터 이벤트마다 API 저장하지 않음 |
| 리사이즈 → CLI가 다른 노트 수정 → 웹 Undo | 크기만 복원, 다른 노트 AI 본문 유지 |
| 이미지 DB 업로드 → URL 폼 미리보기 → 삽입 | `asset:` 이미지의 실제 로딩 확인 |
| CLI 묶음 내보내기 → 새 문서 가져오기 → 웹 새로고침 | 첨부 이미지 로딩·본문 보존 |
| 승인 응답을 3초 지연하고 한국어 입력 | 대기 입력을 승인 후 노트에 반영 |
| API 강제 종료 중 입력 → 페이지 새로고침 → API 재시작 | 연결 끊김 표시·초안 유지·복구 버튼으로 재편집 후 DB 저장 |
| 숫자 X 입력 후 Enter | x=120이 DB에 저장되어 드래그 없이 위치 변경 가능 |
| 편집 완료 버튼 | 편집하던 객체로 포커스 복원; 카메라 강제 이동 없음 |

테스트용 `공동 편집 검증` 문서에서 웹 A와 CLI B 변경을 확인했다. `첨부 복원 검증`에서는 서버 중단 중 작성한 B 초안을 재시작 후 버전 6에 저장했고 숫자 위치 입력은 버전 7에 저장했다. 이 문서와 성능 문서는 로컬 데이터 폴더에만 존재한다.

## 화면과 접근성

1280×900, 500px, 390px 폭을 비교했다. 하단 기본 도구와 Undo/줌을 다른 줄로 배치했다. 390px에서 잘리던 객체 선택 도구는 상단 패널로 바꿨고, 전체 버튼이 화면 안에 들어오는 것을 좌표와 스크린샷으로 확인했다. 화면 폭을 바꿔도 Markdown의 객체 좌표는 바꾸지 않는다.

390×320의 작은 가시 영역에서는 편집 중 하단 도구·탐색 버튼을 숨기고 서식 도구를 화면 안으로 줄바꿈한다. 본문·상단 완료 버튼·서식 버튼이 보이며 편집기 포커스가 유지된다. `prefers-reduced-motion: reduce`에서 전환 시간이 0이고 모션이 제거되는 것을 확인했다. 이미지 폼의 미리보기·닫기·포커스 동작과 키보드 숫자 입력도 확인했다.

실제 iOS/Android 키보드, 물리적 터치 장치, 스크린리더 전체 조합은 검증하지 못했다. 작은 뷰포트 검사는 이들을 대체하지 않는다. 캔버스 자체는 자유 배치 공간이므로 화면 밖 객체는 pan/zoom으로 탐색한다.

## 성능 진단

장비: Intel Core i7-12700KF, 논리 CPU 20개, Windows 10.0.26200, Node 24.19.0, Headless Chrome 151, 1280×900. Vite 개발 서버에서 측정했고 실제 사용자 현장 데이터가 아니다.

문서 구성: 일반 노트 100·500·1,000개, 그리고 100개 중 Mermaid 34개·20줄 TypeScript 코드 33개·일반 노트 33개가 섞인 보드. 객체는 10열 격자, 320×220, 기본 간격 x=360/y=260이다. 모든 노드가 마운트된 상태이며 가상화로 편집기를 없애지 않았다.

`scripts/measure-db.mts`는 원문 파싱과 이동 명령 계획을 워밍업 후 7회 측정한다. 최신 정책 검사까지 포함한 중앙값:

| 문서 | UTF-8 바이트 | 파싱 중앙값 | 명령 계획 중앙값 |
|---|---:|---:|---:|
| 100 | 16,522 | 1.14ms | 2.43ms |
| 500 | 83,672 | 6.11ms | 16.64ms |
| 1,000 | 167,972 | 22.40ms | 57.94ms |
| 혼합 100 | 40,283 | 0.94ms | 2.82ms |

브라우저는 `PerformanceObserver`의 Event Timing과 `requestAnimationFrame` 간격을 수집했다. 클릭·키 입력과 drag/pan/zoom을 다른 구간으로 측정했다. 편집 승인 대기 후 x 입력/Backspace/완료, 실제 이동이 확인되는 drag, pan 5회, 줌 버튼 3회를 실행했다. 최신 측정값:

| 문서 | 키 이벤트 최대 | 클릭 이벤트 최대 | drag 프레임 p95 / 최대 | pan 프레임 p95 | zoom 프레임 p95 |
|---|---:|---:|---:|---:|---:|
| 100 | 40ms | 64ms | 16.8 / 50.0ms | 16.8ms | 66.6ms |
| 500 | 112ms | 216ms | 83.2 / 200.0ms | 16.8ms | 116.7ms |
| 1,000 | 168ms | 360ms | 133.4 / 466.6ms | 49.9ms | 199.9ms |
| 혼합 100 | 40ms | 72ms | 16.8 / 50.0ms | 16.8ms | 116.6ms |

초기 DB 웹 구현에서는 일반 100/500/1,000개 보드의 키 이벤트 최대가 각각 144/1,152/2,216ms였다. 편집 모드 구독을 좁히고 바뀌지 않은 Markdown 렌더링을 재사용했으며, 드래그 미리보기에서 전체 노드 재생성을 제거했다. 같은 장비의 후속 측정에서 키 지연이 줄었다. 다만 측정 중 노트 위치·카메라가 이동했고, 초기 혼합 보드는 Mermaid 노트를 편집했지만 후속은 일반 노트를 편집했으므로 혼합 결과의 직접 개선율은 계산하지 않는다. 중간에는 고정 좌표 drag가 실제 이동을 놓치는 것을 발견해 최종 스크립트에서 대상의 현재 좌표와 이동 결과를 검증하도록 바꿨다.

표본이 작고 16ms 이상 이벤트만 수집하며 드래그 명령 사이 CLI 왕복·유휴 시간이 포함된다. 프레임 p95는 연속 고주파 터치 드래그의 FPS와 같지 않다. 1,000개 보드는 클릭·drag·zoom 지연이 여전히 크다. 이 측정은 **현장 INP 75백분위 200ms 달성 증거가 아니며**, pan/zoom 성능을 INP로 대신 검증하지도 않았다.

재현:

```powershell
# API·웹 실행 후 새 성능 문서를 추가한다. 기존 문서는 지우지 않는다.
corepack pnpm exec tsx scripts/measure-db.mts --seed
$env:BOARDMARK_BROWSER_CLI = 'agent-browser 실행 파일의 절대 경로'
node scripts/measure-browser.mjs
```

결과는 `.boardmark/performance-db.json`, `.boardmark/performance-browser.json`에 쓴다. 같은 이름을 여러 번 생성했다면 사용할 성능 문서를 분리한 데이터 폴더에서 측정하는 편이 명확하다. 빌드·전체 테스트와 동시에 측정하지 않는다.

## 2026-09-09 드래그와 도구 UI 추가 검증

첫 드래그에서 편집 승인이 도착해도 다음 pointermove까지 미리보기가 갱신되지 않는 문제를 회귀 테스트로 재현했다. 첫 수정에서는 승인 대기 중 마지막 포인터 위치를 기억하고 승인 즉시 반영했으며, 승인 전에 놓은 동작은 취소했다. 이 대기 정책은 아래의 사용자 요청에 따른 예측 미리보기로 대체했다. 별도 상태 갱신 때 활성 미리보기를 잃는 문제도 재현했으며, 저장 완료 때는 이전 React 렌더 대신 최신 저장소 좌표로 전환한다. 이전 저장의 정리가 다음 제스처의 미리보기와 편집권을 지우지 않도록 저장 중 제스처 시작을 제한한다.

Windows의 Chromium 자동화 브라우저, Vite 5173 및 실제 SQLite API 4317에서 별도 `드래그 UI 검증` 문서로 확인했다. 실제 acquire/edit 응답 전달에 각각 400ms를 추가했다(관측 왕복 각각 416ms). 포인터를 한 번 이동한 뒤 멈춘 상태에서도 승인 후 위치가 반영됐다. requestAnimationFrame으로 관측한 위치 변화는 `(160,160) → (300,210)` 한 번이며, 저장 중 이전 위치로 돌아오는 프레임은 없었다. 이는 해당 재현 경로의 검증이며 대규모 보드 전체 성능 개선 수치는 아니다.

웹 관리 화면의 공통 버튼 선택자가 캔버스 버튼까지 덮어쓰던 배경·padding을 분리했다. 기본 도구 버튼은 투명하며 선택·포커스 표시는 유지한다. 색상 버튼과 내부 색상칩의 실측 크기는 모두 36×36px이다. 1280×900, 390×640 화면에서 도구와 색상 메뉴를 확인했고, 390×500의 사용자 지정 색상 메뉴는 내부 스크롤로 하단 도구와의 겹침을 방지했다(메뉴 하단 352px, 도구 상단 약 366px). 색상 선택 후 DB 저장 완료도 확인했다. 객체의 저장 좌표는 화면 크기에 맞춰 재배치하지 않는다.

회귀 테스트 4개를 포함한 전체 390개 테스트와 타입 검사가 통과했다. 웹 및 VS Code webview 빌드도 통과했으며 기존 큰 번들 경고는 남아 있다.

추가 사용자 확인에서 정상 드래그의 `편집 가능 여부 확인 중` 메시지가 오류·복구 패널을 잠깐 표시하는 것을 발견했다. 일반 편집권 요청은 저장 상태와 안내 메시지를 변경하지 않도록 수정했다. 이 시점에는 실제 충돌·연결 실패 안내와 서버 승인 전 이동 제한을 유지했다. 실제 브라우저의 승인 응답 전달에 300ms를 추가한 검증에서 안내 패널이 생성되지 않았으며 이동·저장 완료를 확인했다. 웹 세션 및 드래그 테스트 12개(새 회귀 2개), 타입 검사, 웹 빌드가 통과했다.

### 후속 변경: 클라이언트 예측 미리보기

사용자가 승인 대기를 화면 이동에서 분리하도록 요청해, 드래그·리사이즈는 첫 이동부터 로컬 미리보기를 적용하도록 바꿨다. 드롭 후 승인을 기다리는 동안에도 미리보기를 유지하고 상단에는 `변경됨`을 표시한다. 저장은 서버 승인·검증 후에만 실행하며 취소·거절은 최신 확정 좌표로 복원한다. 미반영 예측 좌표는 Markdown 원문이나 DB에 쓰지 않는다.

실제 웹·SQLite API에서 승인 응답 전달을 직접 보류했다. 마우스를 놓았는데도 승인 전달 전에 `(542,274) → (687,322)` 미리보기가 반영됐으며 저장 요청은 없었다. 약 12.8초 후 응답을 전달하자 edit 요청이 한 번 발생했고 위치 변화 없이 `저장됨`이 표시됐다. 이는 지연을 주입한 기능 검증이며 성능 수치가 아니다. 별도 실제 API 세션이 같은 객체를 점유한 경우에도 예측 이동 후 HTTP 409를 전달하자 `(687,322)`로 복원됐고, edit 요청이 없으며 DB 원문·문서 버전이 모두 유지됨을 확인했다.

즉시 미리보기, 승인 전 드롭, 거절, Escape, 화면 종료, 취소한 이전 응답과 새 제스처의 경합, 리사이즈, 저장 중 중복 제스처를 포함해 전체 397개 테스트 및 타입 검사가 통과했다. 웹·VS Code webview 빌드도 통과했다. 본문 편집 진입 정책은 이번 변경 대상이 아니다.

## 현재 한계와 선택적 후속 작업

서버는 하나의 작업 공간 토큰을 사용하는 로컬 단일 프로세스다. 다중 사용자 계정·권한 등급·원격 서비스 운영은 구축하지 않았다. desktop·VS Code는 독립적인 파일 호환 모드이며 빌드·관련 테스트는 통과했지만 이번 실제 편집 E2E의 대상은 웹이다.

변경 감지는 아래 후속 개선에서 커밋 즉시 응답하는 HTTP 대기로 바뀌었다. 변경 때 원문 전체를 받는 방식은 유지한다. 이력과 요청 기록의 자동 정리, 대규모 목록 페이지네이션, 원격 부하 시험은 후속이다. Markdown 포맷의 보존 범위와 첨부 수집 제한은 [설계 결정](../architecture/db-markdown-api.md)과 [운영 안내](../operations/db-workspace.md)에 명시했다.

1,000개 객체의 추가 최적화, 실제 모바일·스크린리더 QA, 첨부/복구 이력 관리 화면을 다음 우선순위로 둔다. Vault 검색·태그·백링크·즐겨찾기·저장된 카메라 뷰·명령 팔레트·템플릿은 별도 기능이다. CRDT/OT, 파일 양방향 자동 동기화, 클라우드 계정·결제·다중 서버는 이번 목표의 비목표로 남긴다.

## 2026-09-09 로컬 편집 지연 개선

서버의 계획·승인·저장 경로가 같은 문서를 반복 분석하던 비용을 줄였다. 가장 최근 계획 하나만 보관하고 문서 ID·DB 버전·명령이 같을 때 재사용한다. 계획과 저장 사이에 다른 작성자가 변경하면 재계산하며, 편집권과 변경 기준 검사는 생략하지 않는다. 클라이언트의 저장·열기·동기화 결과도 한 번만 파싱한다.

저장된 좌표가 편집권 반납 응답까지 기다리던 문제를 응답 보류 테스트로 재현한 뒤 수정했다. 다음 편집권 확보는 이전 반납이 완료될 때까지 기다린다. 웹 변경 감지는 인증된 HTTP 요청을 유지하다 커밋 직후 응답하는 방식으로 바꿨다. 변경이 없으면 기존과 같은 1.5초 간격으로 편집권 상태를 갱신한다. 입력 후 400ms 자동 저장 지연과 렌더링 방식은 그대로다.

`corepack pnpm exec tsx scripts/measure-edit.mts`는 임시 폴더의 별도 SQLite와 메모리 DB만 사용한다. 일반 노트 100·500·1,000개에서 한 노트의 좌표를 매번 바꾸며 계획→승인→저장→반납을 실행한다. 첫 회를 제외한 10회의 중앙값이다. 같은 스크립트를 변경 전 HEAD `ef420b3`의 DB/편집 정책 코드와 수정 코드에 순서대로 실행했다. 테스트·빌드와 동시에 측정하지 않았다.

| 노트 수 | 디스크 DB 변경 전 | 디스크 DB 변경 후 | 메모리 DB 변경 전 | 메모리 DB 변경 후 |
|---|---:|---:|---:|---:|
| 100 | 6.73ms | 4.97ms | 5.17ms | 3.13ms |
| 500 | 27.01ms | 11.98ms | 25.52ms | 11.02ms |
| 1,000 | 92.38ms | 28.81ms | 77.49ms | 26.49ms |

이는 같은 프로세스에서 호출한 서버 처리 시간이며 네트워크·브라우저 렌더링·사용자 체감 시간은 포함하지 않는다. 브라우저 프레임 수치는 재측정하지 않았다. `measure-db.mts`의 계획 측정은 매번 다른 좌표를 사용하도록 바꿔 재사용 적중만 측정하지 않게 했다. 실제 작업 공간의 문서는 변경하지 않았다.

회귀 검증은 저장 후 반납 응답 지연, 즉시 변경 전달, 대기 취소·문서 삭제, 이전 문서의 늦은 알림, 취소된 편집권 요청, 계획 이후 독립 변경 보존을 포함한다. 기존 충돌·복구·재시작 테스트를 포함해 `vitest run --maxWorkers=2`에서 52개 파일·404개 테스트가 통과했고 타입 검사와 웹·API 빌드도 통과했다. 먼저 수행한 전체 실행에서는 변경하지 않은 코드 강조 및 편집 도구 테스트에 각각 시간 초과가 발생했으며 두 파일 모두 단독 실행에서는 통과했다. 테스트 시간 제한은 수정하지 않았다. 웹 빌드의 기존 큰 청크 및 Sandpack 혼합 import 경고는 남아 있다. 실행 중인 API 프로세스는 재시작하지 않았으므로 서버 변경은 재시작 후 적용된다.
